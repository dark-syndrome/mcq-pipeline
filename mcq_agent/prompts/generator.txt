## How to read the concept map

The concept map above is your primary planning tool. Here is how to use each section:

**CONCEPTS** — sorted by testability score (highest first). Prefer concepts rated 4/5 or 5/5 for the bulk of your questions. The `difficulty_range` field tells you the realistic min–max difficulty for each concept — do not write a question outside this range for that concept.

**⚡ confusion pairs** — these are the best seeds for plausible distractors. If a concept lists `confuse with 'MQTT QoS 1'`, use QoS 1 as a distractor option for questions about QoS 2. Always explain in `distractor_rationale` why a learner would make this mistake.

**📝 question templates** — concrete stems provided by the Analyzer. You are not required to use them verbatim; treat them as starting points. Each template already specifies `stem_pattern`, `target_difficulty`, and `bloom_level` — match these when you adapt the template.

**PROCEDURES — failure modes** — use these to write debugging-pattern questions. A failure mode like "forgetting to call WiFi.disconnect() before deep sleep" maps directly to a debugging question where the student identifies the missing step.

**CODE EXAMPLES — testable behaviours** — each listed behaviour is a discrete fact the code demonstrates. Write one question per behaviour maximum. Use `line_annotations` to write targeted questions about specific lines ("what does line 7 accomplish?") rather than only asking about the overall purpose.

**THEMATIC CLUSTERS** — distribute your questions across themes, not just document sections. If one theme has 4 concepts and another has 2, weight your questions roughly 2:1. Do not write all questions from a single section.

**PREREQUISITE CHAINS** — respect learning order. If a chain is [A → B → C], do not write a question about C that assumes knowledge of A without giving the learner the A context in the stem.

<difficulty_rubric>
EASY (Bloom's: Remember/Understand):
- Tests recall of definitions or basic comprehension
- Answer is directly stated in the source
- Only acceptable for concepts with difficulty_range.min_difficulty = "easy"
- Example: "Which layer of the OSI model does MQTT operate at?"

MEDIUM (Bloom's: Apply):
- Tests application of a concept to a specific scenario
- Requires using knowledge, not just recalling it
- Example: "A sensor reports temperature every 30 seconds with intermittent connectivity. Which QoS level minimises missed readings at the cost of possible duplicates?"

HARD (Bloom's: Analyze):
- Tests ability to diagnose, compare, or reason across multiple concepts
- Example: "An ESP32-S3 consumes 18mA in deep sleep instead of 10µA. Which configuration error most likely explains this?"

EXPERT (Bloom's: Evaluate/Create):
- Tests judgment between design trade-offs, no single obvious answer
- Example: "When designing 10,000 battery-powered sensors reporting daily, which combination of protocol and sleep strategy best balances energy, latency, and cost?"
</difficulty_rubric>

<quality_criteria>
Every question MUST satisfy:

1. **Source-grounded**: Correct answer explicitly supported by source. Provide a verbatim source_excerpt.
2. **Uniquely correct**: Exactly one unambiguously correct option (for single_correct type).
3. **Plausible distractors**: Use confusion_pairs and misconceptions from the concept map. Every distractor must have a distractor_rationale explaining the specific confusion it exploits.
4. **Difficulty-matched**: Cognitive demand matches the requested difficulty AND stays within the concept's difficulty_range.
5. **Source-phrase independent**: Correct answer must not copy phrases verbatim from source_excerpt. Paraphrase.
6. **Length parity**: Correct answer word count within ±20% of median distractor word count.
7. **Stem economy**: Every sentence in the stem must be load-bearing. Cut details that are irrelevant to the question being asked.
8. **Self-contained**: No question should require seeing another question to make sense.
9. **Technically precise**: Use exact terminology from the source. Do not paraphrase concept names.
</quality_criteria>

<anti_patterns>
DO NOT generate:
- "Which of the following is true about X?" — tells the learner nothing about the cognitive task
- "What is the purpose of X?" — pure definition recall, banned above EASY
- "According to the text, what does the author say about X?" — tests reading, not understanding
- Questions with absurd distractors (e.g. "a built-in coffee machine")
- Stem inflation: don't list 5 scenario details when only 1 is needed for the question
- Two consecutive questions from the same concept
- More than 2 questions with the same stem_pattern in one batch
</anti_patterns>

<distractor_design>
Build each distractor using one of these strategies (name the strategy in distractor_rationale):

- **confusion_pair**: Directly exploit a confusion_pair from the concept map. The strongest distractors come from here.
- **adjacent_concept**: A related but distinct concept that sounds similar
- **partial_truth**: True in some contexts but not the one specified in the stem
- **common_failure**: A misconception listed in the concept map
- **surface_similarity**: Shares keywords with the correct answer but is semantically wrong

At HARD/EXPERT level, every distractor should be defensible to a learner with partial knowledge — not just plausible-sounding but actually tempting given the stem.
</distractor_design>

<stem_pattern_guidance>
Each question must declare a stem_pattern:
- definition:  "What is X?" — only at EASY difficulty, max 1 per batch
- scenario:    Places concept in a real situation — prefer for MEDIUM and above
- debugging:   Broken/misconfigured system, ask for diagnosis — use procedure failure_modes
- comparison:  Distinguish two or more approaches — use contrasts_with relationships
- procedure:   Test steps in a workflow — use decision_points for interesting variants

Aim for no more than 2 questions with the same stem_pattern in a single batch.
Use question_templates from the concept map as your starting point for scenario/debugging/comparison stems.
</stem_pattern_guidance>
